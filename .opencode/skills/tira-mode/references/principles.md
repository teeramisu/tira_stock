# 原则（6 条，每条一句话）

> 原则是「判断时刻」拿出来用的，不是读完就忘的套话。
> 被问到「为什么这么做」时，说出你用的是哪一条。

## P1 · 证据优先（Prove it works）

「应该可以」「按理说」不算结论。每条结论后面跟一条**可复现的命令**或**可点开的链接**。

判据：别人按你写的命令跑一遍，能得到同样输出。

## P2 · 一件事一个 PR

一个 PR 只做一件事，只碰一个功能区（`pr-scope` 会判定）。
发现的其它问题记下来另开任务 —— 混在一起等于放弃回滚能力。

判据：能一句话说清这个 PR 改了什么；如果要用「并且」，就超范围了。

## P3 · 小步可回退

改动越小，出错时定位越快、`git revert` 越安全。
体量超软上限就拆；拆不动说明你还没想清楚边界。

判据：`git revert <commit>` 之后仓库仍然可运行。

## P4 · 检查不可绕过（Checks are not negotiable）

CI 红了先假定**代码错了**，不是检查错了。
真觉得是检查的问题，就单独开一个 PR 改检查，并给出理由 —— 不要在同一个 PR 里顺手放宽。

判据：`git diff` 里没有为了变绿而删除/弱化断言。

## P5 · 先复现，再修

Bug 修复必须先有一个**失败**的用例（或可复现命令），再让它通过。
没有复现步骤的「修好了」无法验证，也无法防回归。

判据：修复前该命令非 0 退出，修复后 0 退出。

## P6 · 不确定就查，不要填

接口字段、业务口径、历史决策 —— 查代码、查文档、查记忆；查不到就**明确说不知道**，
并给出「需要什么信息才能确定」。

判据：汇报里没有「大概是」「我记得是」这类没有出处的断言。
